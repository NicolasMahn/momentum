# Momentum project conventions

- Each dashboard feature owns the semantic presentation mapping for its icon and colors. The Home card and that feature's screens, charts, dialogs, and controls consume the same named mapping.
- Shared theme files define the palette and general Material surfaces only. Each feature mapping exposes one `ViewColors` (`core/ui/ViewColors.kt`) and wraps its screens and dialogs in `ViewTheme`, which maps the view identity onto `primary` so Material controls and `MomentumButton` defaults follow the view. Outside a `ViewTheme`, `primary` means app-wide chrome only, never a feature identity. `ViewColors` has six roles (`accent`, `onAccent`, `container`, `onContainer`, `label`, `ledge`); outside a view `LocalViewColors` is `neutralViewColors`, the one place that decides the neutral face and its ledge. A presentation with nothing but an icon and colors returns `ViewIdentity`, and `AppDestination.viewIdentity()` in `app/DestinationIdentity.kt` is the one table the header, the Home tiles and the gallery read.
- Preserve an established feature identity when centralizing it. Do not invent a new palette as part of a structural cleanup.
- Product screens and components must not contain color literals or named `Color.` constants, and never decide from a color's `luminance()`: every color comes with the ink and ground made for it, as a named role. `MomentumSurfaceGuardTest` enforces both, together with the surface rules below, no `supportingText` in features, no hand-built day lists in feature models, and no raw window `Dialog`; an exception is an allowlist entry there with its reason.
- Momentum is dark only and has no light scheme: `WorkoutTrackerTheme` takes no theme argument, the palette holds only the dark values, the window theme is dark, and `enableDarkEdgeToEdge` in `core/ui/theme` keeps the system-bar icons light whatever the phone is set to. Never add a light scheme, a theme flag or a `values-night` folder.
- `MomentumButton` in `core/ui` is the only button surface. Do not call Material `Button`, `OutlinedButton`, `TextButton`, `FilledTonalButton`, or `ElevatedButton` in product code; `MomentumSurfaceGuardTest` enforces this.
- `MomentumTabs` in `core/ui` is the only tab surface: labels over a hairline with the chosen one underlined in the view's accent, never a row of buttons or tiles, and never Material's `TabRow`, `Tab` or their variants, which `MomentumSurfaceGuardTest` enforces in `main` and `debug`.
- `MomentumCheckbox` in `core/ui` is the only checkbox surface; do not call Material `Checkbox` or `TriStateCheckbox`. A checkbox with a label is `MomentumCheckboxRow`, so the whole row is one touch target and one element for TalkBack; use the bare box only where nothing labels it.
- `MomentumDialog` in `core/ui` is the only dialog surface (`MomentumBlockingDialog` is its action-less form for work that must not be interrupted); do not call Material `AlertDialog` or `BasicAlertDialog`, which `MomentumSurfaceGuardTest` enforces in `main` and `debug`. Its actions are `MomentumButton`s, a `destructive` confirm is error-colored, and a slot carries richer content such as help. Dialogs are only for guarding unsaved work, an irreversible bulk action, or help the user asked for — never for confirming a day edit.
- Motion is drawn, never laid out: animate with `graphicsLayer`, draw-phase offsets, or a canvas that draws past its bounds, so an animation can never change a measured size and shift the screen. Anything that appears and disappears keeps its space.
- A message that appears and disappears in a layout uses `ReservedMessage`, so nothing under it ever shifts. Its tagged node exists only while there is a message: an empty slot is absent for tests and silent for TalkBack.
- A single-line field with an error is `MomentumTextField` in `core/ui`: the error replaces the floating label, never a `supportingText` line, so an invalid value neither grows the field nor leaves a reserved gap under a valid one. A typed date is `MomentumDateField`, a thin wrapper that owns the one invalid-date message; what a valid date key is lives once in `core/time` (`parseDateKey`, `isValidDateKey`, `requireValidDateKey`).
- "Today" is collected once, in `MomentumApp`, from `localDateKeys` in `core/time`, and every screen receives it as a plain `todayKey: String`. `todayKey` feeds calendar windows, labels and the initial selection only. A draft belongs to the selected date: never key state on today (`remember(todayKey)`), which drops unsaved work at the day boundary; an untouched screen moves to the new day through `FollowTodayEffect` in `core/ui`. `currentDateKey()` is only for a one-shot answer at the moment of an action. Never write a second day-ticking flow or collect one in a feature.
- A recent-day calendar is week-aligned, Monday to Sunday: its date keys come from `calendarWeeksWindow` in `core/time` (which also hides records dated after today), so a day keeps its column and a new row starts each Monday. Days after today are inert ghost cells in `RecentDayCalendar` (no click, no records, no semantics). Never build a rolling day list in a feature.
- Removal is inline and two-step: `MomentumRemoveButton` in `core/ui` arms on the first tap and removes on the second. Day edits never open a confirmation dialog, and a calendar tap only selects the day; it never opens, edits, or removes anything.
- A ledge means "you can press this". Only pressable surfaces (`MomentumButton`, clickable `MomentumCard`) are outlined and raised. Static content sits directly on the background, grouped by spacing; use the flat static `MomentumCard` only for one visual object that needs a ground, such as a chart, and never nest containers. `MomentumCard` in `core/ui` is the only card surface; do not call Material `Card`, `OutlinedCard`, or `ElevatedCard`. A compact row of options is `MomentumChoiceTile` inside a `MomentumChoiceTileRow`, never a hand-built selectable card. Colors come from `GeneratedPalette.kt`, produced by `scripts/generate_palette.py` and never hand-picked or hand-edited; a view identity is `MomentumHues.<Hue>.viewColors()`.
- Words a user sees or hears live in string resources, each feature in its own `res/values/strings_<feature>.xml`, with its German in `values-de`. Both are complete: `StringTranslationTest` fails on any string without German or with other placeholders, and the words Momentum uses for its own ideas are fixed in `docs/glossary.md`. A sentence is one resource with placeholders, quantities are plurals, and user-entered text is shown verbatim. Text decided outside composition (models, notifications, the widget) is a `UiText` from `core/text`, resolved on screen or with `Context.withAppLanguage()` elsewhere; never keep a resolved string in state. Dates and numbers are formatted with the screen's locale through `core/format`; stored keys stay ISO and parsing accepts either decimal separator. Domain code never touches resources. `MomentumSurfaceGuardTest` catches literal product text and fixed English locales.
- The app language is Android's per-app locale (AppCompat below API 33), chosen in Settings or the phone's app-language screen; `core/locale` reads and applies it. `MainActivity` handles the change in place, so a language switch must never recreate it.
- Two licenses apply, and `NOTICE` is the one place that says which: Mo (everything in `feature/mo`, the launcher icon drawables and `docs/pet/`) is under CC BY-NC 4.0, for non-commercial use only, and everything else of Momentum's own is under MIT. Mo's design is never under MIT, wherever he appears, so keep every drawing of him in those paths, where the license is plain.
- Mo's acts (`feature/mo/acts`, rules in `docs/mo-acts.md`) are judged by their pictures, never by the code alone. `scripts/mo_acts.py` renders review sheets and frame-by-frame films on the PC with the app's own drawing code and measures every act for what leaves his box or jumps; it needs no device. Look at an act you wrote or changed in every state it plays in before it is committed.
- A new or changed shared component gets a specimen in the debug gallery (`app/src/debug/.../gallery`). Specimens host the real component with fake state and also back the `@Preview`s. The gallery exists only in the disposable `debug` package, never in `personal`.
- Merge a pull request into `main` only when its `unit-tests` check (`.github/workflows/unit-tests.yml`) is green. A ruleset on `main` requires it; a red check is fixed, never merged past.
- Never run connected Android tests on the owner's phone or any physical device that is not a test phone. Connected-test cleanup can uninstall the tested package and erase app-private data.
- Test on the emulator or on a test phone, with the disposable `debug` package (`com.example.workouttracker.test`). A test phone is one kept for testing only, which any agent may use like the emulator. Each developer lists their own in `~/.config/momentum/test_phones.txt`, outside the repository: one adb serial per line, then a name. Never list a phone someone uses. The build guard must remain enabled; it lets connected tests run only on emulators and listed test phones.
- Reach the test devices through `scripts/emulator.py` only: it takes the emulator when it runs, else an attached test phone (`MOMENTUM_SERIAL` picks one), refuses any other device and any phone with the personal build, touches nothing but the debug package, holds the lock other sessions share the device by, and saves the app's data before replacing it. On a test phone it keeps the screen on while plugged in, because a locked phone stops every run; if it reports the phone locked, ask the owner to unlock it once. The `emulator-explore` skill uses it to try a change the way a person would and report what looks wrong.
- The code's namespace is `de.nicolasmahn.momentum`. The application IDs are older than it and are not to follow it: Android takes another ID for another app, with none of the data. The two `activity-alias` entries in the manifest are the activity's names from before the namespace changed, and the launcher entry sits on one of them: a home-screen icon names its launcher activity, and a launcher may drop an icon whose name is no longer one. Do not move the launcher entry or remove an alias.
- The `personal` build keeps `com.example.workouttracker` for the owner's real installation. Install or restore it only when the owner explicitly asks, and only with a data-preserving update. Never uninstall it or clear its data.
- The `release` build type is the store build: it alone takes the public ID `de.nicolasmahn.momentum` (set per variant in `app/build.gradle.kts`; Google Play never lets a published ID change), is shrunk with R8, and is signed with the upload key in `~/.config/momentum/`, which never enters the repository. Without the key it builds unsigned. Only a release build shows what shrinking broke, so try one with `scripts/emulator.py store-install`, `store-launch`, `store-crashes`, `store-alarms` and `store-remove` before it goes anywhere; code that reads a class or field by name needs a keep rule in `app/proguard-rules.pro`.
- Every merge to `main` goes to Google Play's closed test by itself, unless it changes documents only: `.github/workflows/closed-test.yml` builds the signed bundle and `scripts/play_upload.py` uploads it and sends it for Google's review. The owner asked for this on 2026-11-17, so a merge needs no extra yes on account of the upload; it does mean `main` holds only what testers may get. The version code counts the commits, on from 1298, the highest code used before this history began (`archiveVersionCodes` in `app/build.gradle.kts`), and is never set by hand; `versionName` is. When a change is something a tester will notice, say so in `docs/store/release-notes/`, in every language there and in 500 characters each at most. The workflow's keys are GitHub secrets, copies of the files in `~/.config/momentum/`. Nothing tries the store build on a device before the upload, so a change that reads a class or field by name, or touches the build, is tried with `scripts/emulator.py store-install` before it is merged.
- The privacy policy and the legal notice (Impressum) exist once per language, in `app/src/main/assets/privacy/`. The app shows those files under Settings, About Momentum, and the website is built from them: `scripts/website.py publish` puts the front page (`docs/store/website/`), the policy and the notice on `https://momentum.nicolas-mahn.de/`, as static files in `/opt/momentum-site` on the owner's web server (`deploy/website/docker-compose.yml`; the server's Caddy and its site block belong to the AV_Stuttgart repository). `https://momentum.nicolas-mahn.de/privacy/` is the page Google Play links to. Never edit the files on the server. Publishing makes the texts public under the owner's name: publish only what is merged, and tell the owner what changed. The legal notice holds the owner's postal address because he chose to publish it there; write it nowhere else.
- Before any personal update installation, run `scripts/deploy_personal.py` with an explicit serial and a local archive directory. It must verify the existing data archive and reject pending restore journals before installing. Never bypass failed preflight checks.
- Stored data accepts additions without any conversion. Adding a setting, a field, a record, a collection or a store never needs a schema bump, a migration or an offline conversion: declare it in `AddedAfterBaseline` (`persistence/json/StoredGrowth.kt`), where a missing setting reads its fixed fallback (what the app did before it existed), a missing fact reads as not recorded, and a missing collection or store as empty. Schema 32 is the baseline: what it stored stays required, and `StoredGrowthTest` reads its frozen sample, which is never rewritten. Only removing, renaming or reinterpreting stored data is a breaking change, with a plan of its own. Momentum is an early alpha until it is in the Play Store and the owner is its only user, so a breaking change is allowed when the design needs it, but never for an addition.
- A new persistence store or schema must be included in the versioned backup registry and restore validation, with representative round-trip tests. Do not treat compilation or record counts alone as proof of recoverability.
- Keep backup status honest: a local save is not protected against uninstall until the latest revision has a verified copy outside app-private storage, and disclose the pending-write window.
- Backups do not pile up, and nothing but the rule removes one. `backupsToKeep` in `persistence/backup` is the one place that says which generations stay: the two newest, the last of each of the latest 7 days and of the latest 3 months that hold one. Unchanged records get no new file. An installation removes only generations from its own index (`BackupGenerations`), only after the new one is verified, and never by matching file names in the folder; the one exception is the tidy action a person confirms in Settings, which applies the same rule to the files named by versions from before it. Changing the rule changes what a person can go back to: say so in Settings and in `docs/data-durability.md`.

- Habit days run from 04:00 local time until the next 04:00. Use `habitDate`/`currentDateKey` in `core/time` for record ownership and habit evaluation; real reminder alarms still use wall-clock dates. Preserve stored date keys when changing timing rules.
- Keep recorded facts separate from rewards. Tokens, free passes, freezes, and protected streaks never create records, fill missing measurements, add reading minutes, or increase actual completion counts/rates. Use “recorded”/“completed” for factual data and “protected”/“excused” for game outcomes. A chart may show estimated values only when clearly distinguished from recorded measurements. Tests must prove that protection cannot alter factual statistics when reward rules change.
- Rewards and Mo may judge a task, never a measurement's quality: whether it was done and how much of it was done (Reading's minutes, Activity's days, a use of a substance a person stays away from), never a weight, a rating or how much of a substance. Joy that only a value moving the right way earns is joy a bad week withholds, and that makes skipping the scale the rewarded move exactly when the record matters most. Weight's aim was removed in Block 19 for this; a use is a behavior, not a measurement, which is why staying away may count (Block 22) while a weight's direction may not.
